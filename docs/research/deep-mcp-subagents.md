# Deep evidence dossier: supervisor-as-MCP-server & agent-spawning MCPs (Nov 2026)

## Q1. Harness-native MCP servers that spawn agents

- Claude Code IS an MCP server: `claude mcp serve` runs Claude Code as a stdio MCP server exposing its own tools (file read/edit, Bash) to any MCP client; a running tool call emits progress every 30s since v2.1.271. Session model is one Claude session per server process; connecting client confirms each tool call. [verified: https://code.claude.com/docs/en/mcp#use-claude-code-as-an-mcp-server] (doc recheck 2026-10-24 via https://harnessnotes.com/registry/mcp.json, updated 2026-11-12)
- Claude Agent SDK can be embedded as an in-process `"type": "sdk"` MCP server inside SDK host apps — the documented path for "Claude as a tool" beyond shelling out. [verified: https://code.claude.com/docs/en/mcp] (2026-11)
- Codex: `codex mcp-server` and the standalone `codex-mcp-server` binary were REMOVED (as of Codex CLI 0.154.0); integrations must migrate to the experimental `codex app-server` JSON-RPC interface. [verified: https://developers.openai.com/codex/mcp-server] [verified: https://github.com/openai/codex/blob/main/codex-rs/docs/codex_mcp_interface.md] (2026)
- Codex app-server surface: threads, turns, interrupts, subagents, skills, MCP tool invocation (`mcpServer/tool/call`); explicitly experimental, protocol may change. [verified: https://gist.github.com/oneryalcin/ee2c27e2d8aa040da8fbe7eebcc2ecea] [single-source for the guide's completeness; app-server existence verified via developers.openai.com]
- Community Codex-MCP wrappers: `codex-app-server-mcp` (persistent threads, async turns, resume, interrupts — vs one-shot `codex exec` wrappers). [verified: https://github.com/Goudu666/codex-app-server-mcp] (2026)
- Codex known bug: app-server leaks MCP process stacks for subagents → linear memory growth on Linux. [verified: https://github.com/openai/codex/issues/25015] (2026)
- OpenCode: no first-party "opencode as MCP server" tool surface found; it is an MCP *client* (`opencode mcp add`, OAuth) and has first-party ACP (`opencode acp`) and an HTTP server mode (`opencode serve --port`). [verified: https://opencode.ai/docs/mcp-servers/] [verified: https://opencode.ai/docs/acp/] (2026)
- OpenCode community agent-spawning MCPs: `alejandro-technology/opencode-mcp` (connects Claude Code/Codex/Cursor/Pi hosts to OpenCode subagents), `Traves-Theberge/opencode-mcp` (session + MCP management tools), `nosolosoft/opencode-mcp`, `AlaeddineMessadi/opencode-mcp` (wraps `opencode serve`; v3.0.0 2026-09-16). All small community projects. [verified: https://github.com/Traves-Theberge/opencode-mcp] [verified: https://github.com/nosolosoft/opencode-mcp] (2026)
- Pi (badlogic pi-mono): MCP *client* built-in (`pi mcp add`); no first-party MCP-server mode found. But `pi-server` (formerly pi-orchestrator, v0.81.0+) is a multi-agent orchestration supervisor: process lifecycle, Unix-socket IPC, SQLite session storage, external control. [verified: https://raw.githubusercontent.com/badlogic/pi-mono/main/packages/coding-agent/docs/mcp.md] [single-source: https://deepwiki.com/badlogic/pi-mono/6-pi-server:-multi-agent-orchestration]
- Community Pi-as-MCP: `Baseline-Systems/pi-mcp` — exposes Pi as tools (`pi_prompt`, `pi_continue` with session_id, `pi_fork`, `switch_session`) for multi-turn use without shelling out each turn. [verified: https://github.com/Baseline-Systems/pi-mcp] (2026)
- Generic agent-as-tool wrappers: `j-token/claude-agent-mcp` (OAuth, `claude_query`/`claude_code_task`), `xihuai18/claude-code-mcp` (minimal tools, in-memory Session Manager Map, uses Agent SDK `query()`; notes subagents need `Task` tool). [verified: https://github.com/xihuai18/claude-code-mcp/blob/master/README.md] (2026)
- Cross-harness: `fdarian/oagent` — MCP server exposing ACP-compatible agents (OpenCode, Cursor, Grok, Codex, Claude, Pi) — an existence proof that MCP→ACP bridging is the emerging pattern for "any harness as a tool." [verified: https://github.com/fdarian/oagent] (2026)
- Inference: only Claude Code ships a vendor-supported agent-spawning MCP server; Codex moved that role into an experimental app-server; OpenCode/Pi rely on community wrappers or ACP.

## Q2. Agent Client Protocol (ACP)

- ACP standardizes editor↔coding-agent communication, local (JSON-RPC over stdio subprocess) and remote (HTTP/WebSocket; remote support "work in progress"); reuses MCP JSON types where possible; Markdown-first; custom types for diffs. [verified: https://agentclientprotocol.com/get-started/introduction] (2026)
- Repo has moved to github.com/agentclientprotocol/agent-client-protocol (from zed-industries). [verified: https://github.com/agentclientprotocol/agent-client-protocol]
- Adopters (agents): Claude Agent (via Zed's SDK adapter), Codex CLI (via ACP's codex-acp adapter), OpenCode (first-party `opencode acp`), Gemini CLI, Cursor, GitHub Copilot CLI (public preview 2026-01-28), Cline, Goose, OpenHands, Junie, Docker cagent, Pi (via pi-acp adapter), Qwen Code, Kimi CLI, and 40+ more. [verified: https://agentclientprotocol.com/get-started/agents] (2026-11)
- 25+ agents supported ACP by March 2026; JetBrains co-developing (Junie/IDEA). [verified: https://zed.dev/blog/acp-progress-report] (2026) [single-source for JetBrains framing: https://agentclientprotocol.com/publications]
- ACP Registry launched for one-submission agent distribution. [verified: https://zed.dev/blog/acp-registry] (2026)
- Protocol surface (from spec site): session lifecycle, streaming stop/partial updates, interrupts (user-level cancel of in-flight turns), permission requests, tool-call updates, diff rendering. [verified: https://agentclientprotocol.com/get-started/introduction] (2026)
- Inference (labeled): ACP is interactive-editor-shaped (one user, one session, UI-centric messages); it has no first-class multi-run job model, persistence, or queueing — an orchestrator would use it as a per-agent driver, not as the supervisor's own API.

## Q3. Supervisor-as-MCP-server pattern & long-running calls

- Precedents (orchestrator-as-MCP-server, real projects):
  - `claude-army` — MCP server orchestrating multiple Claude Code agents: create tasks, `check_tasks` (status), `get_task_output`, `get_agent_team`, `cancel_task`, `purge_tasks`. Exactly the spawn/handle/status/cancel tool surface. [verified: https://github.com/robbhimself-1337/claude-army] (2026)
  - `claude-code-teams-mcp` — exposes Claude Code "agent teams" orchestration to any harness: `team_create`, `spawn_teammate` (tmux), `read_inbox`, `task_create`. [verified: https://github.com/cs50victor/claude-code-teams-mcp] (2026)
  - `Agent-MCP` (rinadelph) — multi-agent team formation/coordination via MCP. [verified: https://github.com/rinadelph/Agent-MCP] (2026)
  - `agent-team-mcp` — roles/tasks/dependencies orchestration (paywalled SaaS). [verified: https://github.com/Rumblingb/agent-team-mcp]
  - `@dev-sajjad/agentctx` — MCP server exposing agent-context/session tools. [verified: https://npmjs.com/package/@dev-sajjad/agentctx]
- MCP protocol mechanics for long calls: current revision 2026-07-28; progress notifications (monotonic, correlated), cooperative cancellation, subscriptions; multi-round-trip requests; legacy 2025-11-25 Tasks (experimental, deprecated) vs the new draft "Tasks extension" (`io.modelcontextprotocol/tasks`) for async tool results. [verified: https://harnessnotes.com/registry/mcp.json, updated 2026-11-12] [verified: https://tasks.extensions.modelcontextprotocol.io/specification/draft/tasks]
- Claude Code client behavior (vendor-documented): main-conversation MCP calls >2 min auto-move to a background task; Claude gets a task ID immediately and keeps working (`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`, default 120000; `0` disables). Idle timeout (no response/progress) 5 min remote / 30 min stdio; wall-clock default ~28h (`MCP_TOOL_TIMEOUT`); progress resets idle but NOT wall-clock. Subagent MCP calls are never backgrounded; headless `-p` calls aren't either (unless `CLAUDE_AUTO_BACKGROUND_TASKS=1`) — one-shot runs can end before results arrive. [verified: https://code.claude.com/docs/en/mcp#automatic-backgrounding-of-long-tool-calls] (2026-11)
- Claude Code MCP Tasks extension support: public beta since v2.1.304 — tool call returns once the server ACCEPTS the job; Claude Code polls status; remote-server tasks survive session exit; cancel via /tasks (best-effort; "server may still finish"). [verified: https://code.claude.com/docs/en/mcp#mcp-tasks-that-run-on-the-server] (2026-10/11)
- Output limits (Claude Code): warning at 10k tokens; 25k token / 50k char cap (files spillover; tool can raise to 500k chars via `_meta`). [verified: https://code.claude.com/docs/en/mcp#mcp-output-limits-and-warnings]
- Codex client behavior: default tool call timeout 300s (0.162.1; docs say 60s), startup 30s; timeout → model receives an error result; no tasks-extension support; progress notifications only logged, not shown, and don't extend timeouts. [verified: https://harnessnotes.com/registry/mcp.json → github.com/openai/codex codex-rs sources] (2026-10-24 audit)
- OpenAI cookbook pattern (predecessor): run codex mcp-server with `client_session_timeout_seconds=360000` in Agents SDK — i.e. crank the timeout and hold the call. [verified: https://developers.openai.com/cookbook/examples/codex/codex_mcp_agents_sdk/building_consistent_workflows_codex_cli_agents_sdk]
- Community guidance converges on "accept-and-poll": enqueue work, return a handle fast, expose `report_status`/result tools; honor `notifications/cancelled` end-to-end; don't retry state-changing ops on client timeout. [verified: https://trackmcp.com/blog/mcp-request-timeouts-deadlines] [verified: https://medium.com/@randhir.jassal/mcp-deep-dive-part-9-when-the-tool-takes-minutes-streaming-and-long-running-tools-over-mcp-f0e8f7f87a5b] (2026)
- Client timeout bugs still real: Cowork MCP client times out long calls despite server progress notifications (Claude Code issue #58687). [verified: https://github.com/anthropics/claude-code/issues/58687]
- Inference (labeled): minute-scale supervised runs are now workable over MCP on Claude Code (backgrounding + tasks beta) but NOT on Codex/OpenCode/Pi clients (5-min-class caps or unknown); a supervisor MUST use return-fast + handle + status/cancel tools for portability, which is also the pattern every orchestrator MCP above independently chose.

## Q4. Composition: agents spawning agents via MCP

- What works (evidence): handle/job-object pattern is the de-facto convention — every surveyed orchestrator MCP returns task IDs with separate status/output/cancel tools (claude-army, agent-team-mcp, pi-mcp session_ids, codex-app-server-mcp threads). Structured job objects with deadlines/dependencies exist (agent-team-mcp task IDs + `depends_on` + deadline fields). [verified: URLs above]
- Session/handle conventions: session_id + resume + fork are the recurring primitives (xihuai18 Session Manager Map; pi-mcp `pi_continue`/`pi_fork`; codex app-server persistent threads). [verified: URLs above]
- What breaks:
  - Context/token blowups: Claude Code truncates MCP results at 25k tokens/50k chars (file spillover) — large agent outputs don't reach the orchestrating model intact. [verified: https://code.claude.com/docs/en/mcp#mcp-output-limits-and-warnings]
  - Backgrounding gap: subagent and headless MCP calls never auto-background in Claude Code — recursive agent-spawning-agents deadlocks or loses results in one-shot runs. [verified: https://code.claude.com/docs/en/mcp#automatic-backgrounding-of-long-tool-calls]
  - Process lifecycle: stdio MCP servers are killed on session exit (SIGINT→SIGTERM→SIGKILL within ~500ms on Linux) — in-process job state dies with the client session; remote/HTTP servers survive. [verified: https://code.claude.com/docs/en/mcp (stdio shutdown section)]
  - Resource leaks in nested spawning: Codex subagent MCP process leak issue. [verified: https://github.com/openai/codex/issues/25015]
  - Client-side cancellation is best-effort: "stopping doesn't guarantee the server stops; it may still finish the work." [verified: https://code.claude.com/docs/en/mcp#automatic-backgrounding-of-long-tool-calls]
  - Prompt-injection/trust: Anthropic warns MCP servers fetching external content expose the client to prompt injection — doubly risky when the server spawns autonomous agents. [verified: https://code.claude.com/docs/en/mcp] (warning block, 2026)
- Observability loss (inference, labeled): MCP progress notifications are often not surfaced (Codex logs-only) and tasks-extension adoption is partial, so orchestrators over MCP get weak streaming/observability vs ACP's session/update stream or app-server JSON-RPC events.
- Emerging convention (inference from evidence): supervisor-as-MCP-server returning job handles + status/list/cancel tools, with heavy outputs written to files/artifacts rather than inline tool results; ACP or vendor app-servers used when rich streaming control is needed.
