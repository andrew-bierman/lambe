# External evidence: beads (bd) as local-only supervisor state store
Sources fetched 2026-11-15. Repo: github.com/gastownhall/beads (main). Docs: beads.gascity.com.

## 1. Embedded/local mode is real and serverless — YES, documented, default, not experimental
- [verified: https://raw.githubusercontent.com/gastownhall/beads/main/docs/architecture/dolt.md] (fetched 2026-11-15) "Embedded Mode (Solo / Standalone): In-process Dolt engine — no separate server needed. This is the default… The `bd` binary includes everything; just `bd init` and go." "Zero ops: no server, no ports, no PID files." Data in `.beads/embeddeddolt/`.
- [verified: same dolt.md] "Embedded mode includes everything in the `bd` binary; no separate Dolt install is needed." Standalone `dolt` CLI is only for server mode. Embedded "links the Dolt 2.6.0 engine into `bd` (`dolthub/driver` v2.4.1 with `github.com/dolthub/dolt/go` at the v2.6.0 release, in `go.mod`), no matter which `dolt` CLI is on your PATH." → in-process Go library, not shelling out.
- [verified: README https://raw.githubusercontent.com/gastownhall/beads/main/README.md] "Embedded (default) — `bd init`. Dolt runs in-process… single writer. Recommended for most users." Only the HTTP backend is labeled "(experimental)"; embedded is not.
- Constraints: single-writer via file lock; concurrent access → "database is locked" errors, switch to server mode [verified: dolt.md Troubleshooting]. A sole supervisor daemon is fine; two writers are not.
- If Dolt server absent: embedded `bd` never needs one (engine is in the binary). Server mode fails with "dial tcp … connection refused" [verified: dolt.md].
- Git-free, never-syncs operation documented: `bd init --quiet --stealth` with `BEADS_DIR`; "It does not stop Dolt network sync; set `dolt.local-only: true` for that" [verified: README Git-Free Usage]. Sync is manual (`bd dolt push`); no evidence of automatic push.
- Caveat: schema-version guard exits if DB migrated by newer binary [verified: README]. `bd doctor --fix` not available in embedded mode; embedded runs only artifacts/conventions/pollution checks [verified: dolt.md].

## 2. Structured fields for machine state — partial yes: free-form JSON metadata + native timestamps
- Arbitrary JSON metadata per issue: `bd update --metadata '<json>'` / `--set-metadata key=value` (repeatable) / `--unset-metadata` [verified: https://beads.gascity.com/cli-reference/update].
- Queryable: `bd list --metadata-field key=value` (repeatable, exact match) and `--has-metadata-key` [verified: https://beads.gascity.com/cli-reference/list]. [single-source on comparability: docs show equality only; no numeric/range comparison on metadata documented. Inference: timestamps as metadata are not range-queryable via bd.]
- Native wake-at semantics: `--defer` "Defer until date… hidden from bd ready until then, then auto-wakes to open" [verified: update ref]; filters `--deferred`, `--defer-before/after` (relative like `+6h`), `--due-before/after`, `--overdue` (due_at in past) [verified: list ref]. → "next_wake_at <= now" maps to defer_until/due_at, not metadata.
- session ids: `--session` / `CLAUDE_SESSION_ID` recorded as `closed_by_session` [verified: README HTTP section + update ref]; no indexed session-column query — store as metadata or `--external-ref` (exact-match filter exists, `--external-ref`, `--external-contains`) [verified: list ref].
- Wisp plane has machine-ish types: `--wisp-type` filter lists "heartbeat, ping, patrol, gc_report, recovery, error, escalation" [verified: list ref] — evidence beads already models liveness-style ephemeral rows (ephemeral wisps not exported to JSONL; `bd purge` reclaims them) [verified: dolt.md]. No doc found of anyone storing supervisor state in beads; that use appears novel [inference].
- Custom issue types exist behind `types.custom` config [verified: update ref `--type`]; custom *typed* fields (beyond metadata JSON) not documented anywhere I could find [inference from absence in CLI refs + schema docs].
- `--json` output on list/ready/show [verified: README]. Sub-issues (hierarchical ids), links (`blocks`, `relates-to`, etc.) [verified: README].

## 3. Write characteristics — workable but each write costs a Dolt commit + engine startup
- Per-invocation startup: "Each `bd` command starts the embedded engine, so a script or agent loop that calls `bd` hundreds of times pays that startup every time. `bd batch` runs a limited set of write commands… in one transaction and one process." [verified: dolt.md]. A checkpoint every 30–60s via CLI = engine boot each time; mitigate with `bd batch`, or resident process.
- History growth: embedded auto-commit is ON by default — "each `bd` write command creates a Dolt commit" [verified: dolt.md]. Per-issue opt-out: `--no-history` "skip Dolt commits, not GC-eligible" [verified: update ref]; `dolt.auto-commit: on|off|batch` config [verified: dolt.md].
- Measured perf (docs, M2 Pro, 10K-issue db): Create 2.5ms, Update 18ms, Bulk close 100 issues 1.9s (~19ms/write) [verified: https://raw.githubusercontent.com/gastownhall/beads/main/BENCHMARKS.md]. (Note: file references sqlite bench harness names; treat numbers as directional.) [single-source]
- Garbage/history hygiene: `bd prune`/`bd purge` delete closed beads; `bd flatten`/`bd compact`/`bd gc` reclaim Dolt storage; Dolt GC is generational — squashed history in old generation survives default `dolt gc`; use `dolt gc --full` [verified: dolt.md "Why a garbage collection can reclaim nothing"]. Known Dolt 2.3.x `DOLT_RESET('--hard')` regression affected compact/flatten on old releases; pinned 2.6.0 measured clean [verified: dolt.md]. Issue-history growth from frequent updates is inherent (version history is the point); compaction ("memory decay") summarizes old closed tasks [verified: README].
- Never pushing: local-only is a supported configuration (`dolt.local-only: true`, `--stealth`, no dolt remote needed); remotes are opt-in via `bd dolt remote add` [verified: README + dolt.md]. No documented side effect of having zero remotes; `bd dolt push` is the only push path and is manual [verified: dolt.md]. Note: `bd init` auto-detects git `origin` and persists `sync.remote` on brand-new projects [verified: dolt.md] — harmless but nonzero config footprint. [inference]
