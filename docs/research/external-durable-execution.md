# External evidence: durable-execution foundations for a local coding-agent supervisor
Compiled 2026-11-15. All URLs fetched live during compilation. Labels: [verified]=fetched primary source (license/doc text entails claim); [vendor-doc]=vendor documentation (fetched); [user-report]=practitioner post/thread; [single-source]=only one source found.

## Restate
- License: BSL 1.1; each release converts to Apache-2.0 four years after release. Internal/production use of your own services explicitly permitted; forbidden use is running a public Restate platform service for third parties. [verified: https://github.com/restatedev/restate/blob/main/LICENSE — "Change Date: 4 years after release", "Change License: Apache 2.0"]
- Footprint: "single self-contained binary. No external dependencies needed" (brew/npx/binaries/docker). [vendor-doc: https://docs.restate.dev/installation]
- Durability: single-node persists to disk; "fsyncs committed data to disk before acknowledging network messages". Same binary scales to HA cluster. [vendor-doc: https://docs.restate.dev/server/overview]
- Recovery semantics: service crash → "Any ongoing executions are retried on new instances"; single node recovers from disk. [vendor-doc: https://docs.restate.dev/foundations/key-concepts]
- Fit constraint for process supervision: your code runs as separate HTTP-addressable services (convention port 9080); Restate server sits in front and journals calls. SDKs: TS, Java, Kotlin, Python, Go, Rust, Ruby. [vendor-doc: https://docs.restate.dev/services/deploy/standalone ; key-concepts]
- Community framing: single-binary pitch vs Temporal's pull-worker model is the main differentiator per HN discussion (Show HN, Jun 2024; maintainer comment Mar 2025). [user-report: https://news.ycombinator.com/item?id=40659160 ; https://news.ycombinator.com/item?id=43493665]

## Temporal
- License: MIT (server). [verified: https://github.com/temporalio/temporal/blob/main/LICENSE]
- Local footprint: `temporal server start-dev` is a single binary, `--db-filename` persists workflow state to a local SQLite file; flagged "WARNING: The development server is not intended for production use." Embedded in-process Go server exists "for local development and testing scenarios". [vendor-doc: https://docs.temporal.io/cli/server ; https://docs.temporal.io/self-hosted-guide]
- Production self-host: multi-service cluster (frontend/history/matching/worker) + database + production checklist; user: "Self hosting is daunting. Temporal is not a single process with a single run command." [vendor-doc: docs.temporal.io/self-hosted-guide ; user-report: https://medium.com/@mailman966/my-journey-hosting-a-temporal-cluster-237fec22a5ec]
- Payload/history limits that bite verbose agent logs: 2 MB default per-payload limit (configurable self-hosted, fixed 2 MB on Cloud), 4 MB per gRPC transaction, event history capped at 51,200 events / 50 MB — exceeding terminates the execution; docs recommend passing references, not blobs, and Continue-as-New. [vendor-doc: https://docs.temporal.io/self-hosted-guide/defaults ; https://docs.temporal.io/workflow-execution/limits ; https://docs.temporal.io/troubleshooting/blob-size-limit-error]
- Operating burden, user reports: Loop ran Temporal Cloud then self-hosted Feb 2025 on RDS Postgres, migrated again early 2026 to ScyllaDB for cost, and "invested heavily in observability tooling" once Temporal became mission-critical. Datadog (4 yrs self-hosting, dozens of clusters) titled their talk "Surviving the Challenges of Self-Hosting Temporal … hard lessons and high-stakes incidents" (Mar 2025). Daylight.ai moved off Temporal Cloud (~500 starts/s) for cost/data-locality. [user-report: https://www.loop.com/engineering-blog/temporal-at-loop---evolution-and-scaling ; https://temporal.io/resources/on-demand/surviving-the-challenges-of-self-hosting-temporal-at-datadog ; https://daylight.ai/blog/how-we-migrated-off-temporal-cloud-without-downtime]

## River (Go, Postgres)
- License: MPL-2.0. [verified: https://github.com/riverqueue/river/blob/master/LICENSE]
- Shape: embedded Go library (client in your binary; no server process). Postgres primary, experimental SQLite support. Workers are Go generics (`JobArgs`+`Worker`); Java/Ruby/Rust/TS can insert jobs but Go executes. Requires migrations (bundled CLI). [vendor-doc: https://riverqueue.com/docs]
- Retries: default max 25 attempts, quartic backoff `attempts^4 + rand(±10%)` → last retry ~3 weeks after first run; fully customizable per client/worker. [vendor-doc: https://riverqueue.com/docs/job-retries]
- Resumption (core, not Pro): `ResumableStep` / `ResumableStepCursor` record completed steps/cursors in job metadata so retries skip finished work; transactional checkpoint variants (`ResumableSetStepTx`) commit progress with DB writes; caveat in docs: default checkpoints persist only at attempt end (mid-step crash can lose progress) and "External side effects still need to be idempotent." [vendor-doc: https://riverqueue.com/docs/resumable-jobs]
- Paid tier: River Pro (commercial) adds workflows, sequences, global concurrency limits, DLQ, batching, encrypted jobs. Core covers queues, cron, unique jobs, cancellation, graceful shutdown, leader election. [vendor-doc: https://riverqueue.com/docs (nav: "Pro" tags) ; https://riverqueue.com/docs/pro]

## Oban (Elixir)
- License: Apache-2.0 core (repo moved to oban-bg/oban); Oban Pro is a separately licensed package (Smart engine: global concurrency/rate limits/partitioning; workflows, batches). [verified: https://github.com/oban-bg/oban README + Apache-2.0 badge]
- Footprint: library inside your Elixir/OTP app's supervision tree; no external server. Engines: PostgreSQL, MySQL, SQLite3. Requires Elixir 1.15+/Erlang 24+. [vendor-doc: same README]
- Job semantics: jobs retained in DB for inspection (rows not deleted), unique jobs, cron with dedup, mid-execution cancel across nodes, graceful-shutdown grace period, orphaned jobs "may be rescued later". [vendor-doc: same README]
- Note: workflow features (fan-out/fan-in, deps between jobs) are Pro, not core. [vendor-doc: same README]

## Hatchet
- License: MIT. [verified: https://github.com/hatchet-dev/hatchet/blob/main/LICENSE]
- Architecture: API server + engine + your workers over bidirectional gRPC; "PostgreSQL is the source of truth"; self-hosted can run Postgres-only ("In many deployments that's enough—no separate broker required"), RabbitMQ optional for high throughput. [vendor-doc: https://docs.hatchet.run/v1/architecture-and-guarantees]
- Guarantees: "at least once: … a task can run more than once, so your task code should be idempotent (or otherwise safe to retry)". Explicitly not for sub-ms dispatch or 10k+ tasks/sec without tuning; bottlenecks listed: DB connection limits, payloads >1MB. [vendor-doc: same page]
- Footprint: `hatchet server start` CLI (wraps Hatchet Lite, single docker image, dev/low-throughput prod); embedded local mode "with no Docker" for dev; full docker-compose = Postgres + optional RabbitMQ + engine/API/dashboard. [vendor-doc: https://docs.hatchet.run/self-hosting]
- Positioning, maintainer statement on HN (~Feb 2026): "if everything fits in a single database transaction, you don't need a durable execution platform, you need a task queue with retries — our argument at Hatchet is that this is many (perhaps most) async workloads." [user-report/vendor-adjacent: https://news.ycombinator.com/item?id=46245238]
- Pitched for AI agents/long-running workflows (README: background tasks, AI agents, durable workflows; Postgres durability "particularly easy to self-host"). [vendor-doc: https://github.com/hatchet-dev/hatchet]

## Inngest
- License: SSPL v1.0 with an irrevocable future grant to Apache-2.0 effective on the 3rd anniversary of each release. Self-hosting your own instance is permitted; SSPL is not OSI-approved. [verified: https://github.com/inngest/inngest/blob/main/LICENSE.md]
- Footprint (self-host): single CLI binary containing all services; default = SQLite persistence (./.inngest/main.db) + embedded in-memory Redis for queue/state with periodic snapshots; external Postgres/Redis supported; "Inngest's support team does not guarantee direct support for self-hosted instances." [vendor-doc: https://www.inngest.com/docs/self-hosting]
- Model: your functions are HTTP endpoints (SDK); each `step.run()` result is persisted and memoized on replay; "Code outside a step can run again each time the handler replays." Limits: 1,000 steps/function, 4 MiB per step result, 32 MiB run state, 2 h step timeout. [vendor-doc: https://www.inngest.com/docs/durable-execution/durable-workflows ; /docs/durable-execution/limits]
- Boundary statement (vendor blog, Oct 23 2026): "The Queue is Durable. Your Worker is Not. Durable execution means nothing gets lost. It doesn't mean your worker picked it up, finished it (or finished it exactly once)." [vendor-doc: https://www.inngest.com/blog]

## Other verified alternatives
- DBOS (library-only durable execution): TS/Python/Go/Java/Rust SDKs, MIT, "entirely contained in this open-source library, there's no additional infrastructure"; workflows/steps/queues/schedules checkpointed in Postgres; supports fork-from-step recovery. [verified: https://github.com/dbos-inc/dbos-transact-ts README, MIT badge] Go SDK is real and active: dbos-transact-golang v1.0.0 released 2026 (release notes visible), issues opened through Oct 2026, and pkg.go.dev shows a `sqlite` driver package (pure-Go modernc.org/sqlite) → library-only durable execution on SQLite. [single-source, from GitHub releases + pkg.go.dev listings fetched Nov 2026]
- pgmq: Postgres extension message queue, "No background worker or external dependencies, just Postgres SQL objects", visibility timeouts, PostgreSQL license; adopted by Supabase/Tembo. The minimal-hand-rolled baseline. [vendor-doc: https://github.com/pgmq/pgmq]
- Graphile Worker: MIT, Postgres-backed job queue for Node/TS. [verified: https://github.com/graphile/worker/blob/main/LICENSE.md]
- Windmill: AGPLv3 source core (backend/frontend) + proprietary snippets + non-open "Community Edition" binary; requires Postgres + server container + worker containers. Heavyweight for single-user local. [verified: https://github.com/windmill-labs/windmill/blob/main/LICENSE ; vendor-doc: https://www.windmill.dev/docs/advanced/self_host]
- pg-boss: NOT verified this pass (not fetched) — omitted.
- Bun-runtime-native durable options: none found that are Bun-specific; Bun appears only as the Bun ORM in River docs (unrelated to Bun runtime). No verified Bun-native durable-execution SDK found. [single-source: absence of evidence in fetched docs]

## Coding-agent-specific recovery primitives (the boundary)
- Claude Code has a built-in supervisor and resume: `claude daemon run/status/logs` (background-session supervisor), `claude respawn <id>` (restart session "with its conversation intact"), `claude --resume <id|name|transcript-path>`, `claude -c`, `--session-id` (client-chosen UUID). [verified: https://code.claude.com/docs/en/cli-reference, fetched Nov 2026]
- Codex CLI has resume: `codex resume [--last|SESSION_ID]`, `codex exec resume [SESSION_ID]`; sessions saved as JSONL under ~/.codex/sessions. Added in 2025 (v0.30/0.36), current in 2026 docs. [vendor-doc/user-report: https://learn.chatgpt.com/docs/developer-commands ; https://github.com/openai/codex/discussions/1076]
- OpenAI's own coding-agent orchestrator, Symphony (open spec + reference service, 2026, ~25k stars): polls an issue tracker, creates isolated per-issue workspaces, launches agent sessions, gates on "proof of work" — described nowhere as being built on a durable-execution engine; orchestration = tracker + workspace + WORKFLOW.md hooks. Closest public analog to the caller's supervisor. [user-report, secondary sources: https://rywalker.com/research/symphony ; https://betterstack.com/community/guides/ai/openai-symphony — single-source on internals]
- Hand-rolled cost/miss evidence: HN on DBOS Go (Oct 2025): "the burden of creating idempotent sub-steps in the workflow falls on the developer, regardless of checkpoints"; another commenter: "we rolled our own in a few hundred lines of Python." [user-report: https://news.ycombinator.com/item?id=45412938 ; https://news.ycombinator.com/item?id=47160065]

## Comparative: fit for a local-first coding-agent supervisor
1. Every option here reduces to: durable state in a local store (SQLite/Postgres/disk) + a process that owns scheduling, retries, and observability. They differ in what runs as an external process and how much you must restructure code. [synthesis of fetched sources]
2. Footprint ranking (verified): River/DBOS/Oban/Graphile/pgmq = embedded library (your binary + a database; DBOS Go and River both have SQLite paths; Oban has a SQLite3 engine) < Inngest/Restate = one extra always-on binary, zero external deps < Hatchet Lite = one docker image (embedded no-Docker dev mode exists) < Temporal = dev-mode single binary, production = multi-process cluster + DB < Windmill = Postgres + server + workers. [vendor-docs cited above]
3. Guarantee boundary: all engines deliver at-least-once invocation + journaled state, and ALL explicitly push side-effect idempotency/resumption onto you — Hatchet: "your task code should be idempotent"; River: "external side effects still need to be idempotent"; Inngest: "it doesn't mean your worker … finished it exactly once". [vendor-docs cited above]
4. For coding agents the side effect IS the agent process, and both major agent CLIs already own work-level resumption (`claude --resume/respawn`, `codex resume`) with client-selectable session IDs. So the framework's job is exactly: launch with args, enforce timeouts, detect exit/crash, retry-with-backoff, relaunch mapped to the SAME session resume ID, record output paths, cancel. That is queue+process-supervision territory; step-journaling frameworks add value only if you model multi-phase "responsibilities" (plan → implement → verify → PR) as resumable steps — River ResumableStep or Inngest steps give that for free; a hand-rolled loop re-implements ~200-400 lines of it (HN evidence says people do). [synthesis; agent-CLI claims verified above]
5. Temporal-specific trap for this shape: agent transcripts/output easily exceed its 2 MB payload / 4 MB transaction / 50 MB history caps → you'd be forced into pass-the-reference plumbing everywhere. [vendor-doc: docs.temporal.io limits pages]
6. Licensing vs single-user local use: BSL Restate, SSPL Inngest, proprietary-binary Windmill CE, and commercial tiers (Oban Pro, River Pro, Hatchet EE features, Temporal Cloud) are all unrestricted for self-use of core; nothing blocks a local supervisor. MIT/MPL/Apache cores: Hatchet, DBOS, Temporal server, Oban, Graphile, pgmq; River core MPL-2.0. [verified license files above]
7. Single-developer friction evidence: Temporal self-hosting pain is the best-documented (Loop/Datadog/Daylight/Medium reports); DBOS messaging drew the "rolled our own instead" reaction; Hatchet's own maintainer says most async workloads only need "a task queue with retries". [user-reports cited above]
