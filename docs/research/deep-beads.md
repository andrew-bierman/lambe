# Deep Beads technical survey (evidence dossier)
Collected 2026-11-15. Sources are dated at citation. Docs at beads.gascity.com (built from main); CHANGELOG at github.com/gastownhall/beads/blob/main/CHANGELOG.md. Note: local `bd` on this machine is **1.3.4**, not 1.3.2 as the caller stated.

## 1. Claims/leases semantics
- Claim: `bd update <id> --claim` or `bd ready --claim` — atomic CAS setting assignee+in_progress; idempotent if already held by you; first-claim-wins across workers [verified: https://beads.gascity.com/multi-agent/coordination.md, 2026-11].
- Lease lifecycle: claim stamps `lease_expires_at = now + TTL` (**default 5m**, `WithLeaseTTL` override — no documented config key/env for CLI TTL; library option only) + `heartbeat_at`; `bd heartbeat` (alias `hb`) is owner-only, pushes expiry forward; fails once lease reclaimed/closed so worker learns to stop [verified: commit e97839a "feat(lease): land the leasing stack + schema v54", github.com/gastownhall/beads/commit/e97839a2, 2026; verified: https://beads.gascity.com/cli-reference/heartbeat.md].
- Reaper: `bd reclaim --older-than <grace>` (default grace **10m = 2×TTL**) reverts stale-lease in_progress→open, clears assignee, records recovery event. It is a client-run command ("Run it from a supervisor on a timer"), **no built-in background reaper** [verified: https://beads.gascity.com/cli-reference/reclaim.md].
- Expiry ≠ revocation: a dead worker's issue stays in_progress until someone runs reclaim; earliest failover eligibility ≈ TTL + grace + poll cadence [verified: https://blog.criticaldeveloper.com/posts/2026-10-14-beads-worker-recovery-ownership-and-concurrency/, 2026-10-14].
- Actor identity: assignee doubles as lease owner; actor = plain string resolved `--actor` > `BEADS_ACTOR` > `git config user.name` > `$USER` > "unknown". No agent registry; identity is unauthenticated convention [verified: https://beads.gascity.com/reference/configuration.md (Actor Identity Resolution), 2026-10-26].
- Enforcement: fencing is real at the store (row_lock cell rewritten on every lease-mutating path so racing heartbeat/reclaim/close hit 1213/1205 serialization conflicts and retry — no silent zombie cell-merge), but `--actor` is caller-asserted, not authenticated [verified: commit e97839a; verified: https://beads.gascity.com/cli-reference/serve.md ("An actor on an HTTP request is caller-asserted provenance")].
- CAS guards for supervisors: `bd update --if-assignee/--if-status` (mismatch → exit **13**, nothing written); `bd unclaim --if-assignee` atomic CAS release; `bd unclaim --force` / `bd update --force` for admin override [verified: https://beads.gascity.com/cli-reference/update.md, /cli-reference/unclaim.md].
- **Leases are per-replica**: leases table is ephemeral, node-local, in `dolt_ignore` — never versioned/pushed/federated; heartbeats write no Dolt commit. Cross-machine visibility rides only status/assignee (stale by one sync interval). `bd reclaim` skips leases granted by another replica unless `--any-replica` (for departed replicas) [verified: https://beads.gascity.com/cli-reference/heartbeat.md, /multi-agent/federation.md (Leases are per-replica)].
- Node guard: opt-in `BEADS_NODE_ID` / `bd config set node_id` (writes user-global `~/.config/bd/config.yaml`; never commit to tracked config). node_id names the STORE, not host — all clients of one dolt sql-server share one value. No hostname fallback; unset degrades to unguarded (every lease treated local) [verified: https://beads.gascity.com/multi-agent/federation.md; verified: CHANGELOG [1.2.x] node_id entry, 2026].
- **Wisp claims take NO lease** (ephemeral rows unversioned): heartbeat refuses them, reclaim will not recover a dead holder of a wisp claim [verified: CHANGELOG "A ready claim that wins an ephemeral row..." §1.1.2-era, lines ~10140-10150].
- Claim pools: `claim.pools` config lets any actor claim issues assigned to a pool alias; on lease expiry reclaim clears assignee (does not return to pool) [verified: https://beads.gascity.com/reference/configuration.md (Claim Pools)].
- Failover verdict: a supervisor CAN rely on TTL failover but must run `bd reclaim` itself, on the granting replica, with grace > sync interval; there is no autonomous reaper and no cross-lease fencing between replicas. [inference from above]

## 2. Workflow vocabulary
- Molecules = epics whose children flow through `bd ready` (`bd mol pour/bond/squash/burn/wisp`); formulas = TOML/JSON templates (`bd cook` → proto, ephemeral by default, `--persist` for template); protos stamped into molecules with `--var` substitution [verified: https://beads.gascity.com/workflows/molecules.md, /workflows/formulas.md, /cli-reference/cook.md].
- Gates: issue-typed wait conditions — types human, timer, gh:run, gh:pr, bead. Entry-gate blocks a step; exit-gate (step `type="gate"`) makes step a prep task. Closed by `bd gate resolve` (manual/human) or `bd gate check` evaluating real world (timer: now > created_at+timeout; gh via `gh` CLI). **No scheduler: docs instruct running `bd gate check` from cron/CI/orchestrator loop** [verified: https://beads.gascity.com/workflows/gates.md, /cli-reference/gate.md].
- Gate wake: `bd gate add-waiter <gate> <waiter>` registers for a wake notification via `bd gate wake` (used by `bd done --phase-complete`) — a pull/notification registry, not a push scheduler [verified: https://beads.gascity.com/cli-reference/gate.md (add-waiter)].
- Defers: `bd defer --until` = snooze; `bd update --defer`. **Auto-wake is lazy**: "once --until passes, the next ready-front read returns the issue to open automatically"; configuration.md confirms `bd ready` writes because it "first wakes issues whose defer time has passed". No date `--until` = indefinite icebox until `bd undefer` [verified: https://beads.gascity.com/cli-reference/defer.md; verified: configuration.md (versioned-history section)]. Verdict: **all time-based behavior is client-polled; bd has no internal scheduler daemon**.
- Wisps: ephemeral-flagged issues excluded from federation push by default (`federation.exclude_types` default `[wisp]`), purged via `bd purge`/`bd mol wisp gc`, promoted via `bd promote`/`--persistent`/`bd mol squash` [verified: https://beads.gascity.com/workflows/wisps.md].
- Coordination shards: id creation coordinates through "the create-coordination cell ... (4096 shards shared by hash)" — a retaining sweep holds the shard of each retired id, briefly blocking/conflicting with creates hashing to the same shard [verified: CHANGELOG [Unreleased=1.4.0], retain-ids entry].
- Molecule conveniences: `bd ready --mol`, `--gated` (gate-resume dispatch), `bd close --continue/--claim-next`, `bd swarm`, merge slots (`bd merge-slot acquire/check/release` — one exclusive primitive per project) [verified: cli-reference/ready.md, close.md, merge-slot.md, coordination.md].

## 3. Programmatic surface for an orchestrator
- `--json` contract documented per command with `schema_version` envelope (`BD_JSON_ENVELOPE=1`, envelope default in v2.0); list commands emit raw arrays today; contract pinned by `protocol/json_contract_test.go` [verified: https://beads.gascity.com/reference/json-schema.md, last reviewed 2026-11-07].
- Exit codes: 1 general; **13** stale CAS guard (retry pointless); **14** migration freeze (retry later); `--max-rows` exceeded = 2 [verified: json-schema.md; cli-reference/ready.md].
- `bd batch`: single-transaction multi-write (close/update/create/dep add/remove only), one DOLT_COMMIT; rollback on any error; designed to kill per-invocation write amplification [verified: https://beads.gascity.com/cli-reference/batch.md].
- HTTP server: `bd serve` loopback HTTP API, OpenAPI doc at `/v0`, `GET /v0/beads/context` capability discovery. Optional bearer-token file auth; `--allow-non-loopback` requires token; no TLS; hooks don't fire over HTTP; actor caller-asserted; graceful shutdown SIGHUP/SIGINT/SIGTERM [verified: https://beads.gascity.com/cli-reference/serve.md].
- Subscribe vs poll: **events journal** = per-mutation binlog (`bd events tail --since <seq> --follow` polls 1/s; HTTP `GET /v0/beads/events?since=`), gapless seq per replica, retention floors 7d/100k rows, resumable cursor, `truncated` 410 semantics. **SSE `GET /v0/beads/events:watch`** (text/event-stream, Last-Event-ID resume, 48-stream cap) exists in main docs [verified: https://beads.gascity.com/reference/events-journal.md]; CHANGELOG's only `events:watch` mention is in [Unreleased=1.4.0] [verified: CHANGELOG line 3804] — **treat SSE watch as 1.4.0, not 1.3.x; 1.3.x has poll-based tail/follow only** [inference, single-source on the negative].
- Caveats for orchestrator: journal is per-replica/per-branch, off by default, and does NOT cover sync (`bd dolt pull`), raw SQL, or compaction — a federated consumer must re-baseline after every sync [verified: events-journal.md (What the journal does not cover)].
- Hooks: `.beads/hooks/` on_create/on_update/on_close fire-and-forget scripts (CLI only, not over serve) [verified: events-journal.md (three event systems table)].
- Custom types/statuses: `types.custom` (db-stored), `status.custom` with behavior categories (active/wip/done/frozen — controls `bd ready` eligibility), `types.infra` routed to wisps table, `types.retained` (1.4.0) [verified: configuration.md (Custom Statuses and Types; types.retained)].
- Idempotent create: `bd create --id <id>` (never overwrites; graph plans pin ids too). **Tombstones (`--retain-ids`, `id_tombstones`, `idempotency_expired` 410) are [Unreleased=1.4.0]** [verified: wisps.md (Retiring ids); CHANGELOG lines 184-207 in [Unreleased]]. In 1.3.2, purged ids are simply reusable.
- Optimistic concurrency: `bd show --json` returns `revision` guarded-write token [verified: json-schema.md (bd show)].

## 4. Sync/federation
- Mechanics: sync is Dolt remotes — `bd dolt push`/`pull` with cell-level merge; `bd sync` = pull + conflict check + `recompute-blocked` repair + push. Auto-push opt-in (default off; concurrent git-protocol pushes can corrupt remote history) [verified: https://beads.gascity.com/architecture/dolt.md; configuration.md (auto-push)].
- `federation.*` config: `federation.remote`, `federation.sovereignty` (T1-T4), `federation.allowed-remote-patterns`, **`federation.exclude_types` default `[wisp]`** [verified: configuration.md (Sync and Federation)]. Peer-to-peer `bd federation add-peer/sync/status` (requires CGO/direct DB access), conflict → pause for manual resolution or `--strategy ours/theirs`; hub-spoke/mesh/hierarchical topologies; multi-writer needs `dolt sql-server` (3306 SQL + 8080 remotesapi) [verified: https://beads.gascity.com/multi-agent/federation.md].
- Criss-cross hazard: federation peers that pull from each other create multiple merge bases; Dolt 2.6.0 changes merge behavior (virtual-base ORT-like) — some previously-silent merges now conflict; single-remote push/pull unaffected [verified: architecture/dolt.md (Dolt 2.6.0 notes)].
- Leases never federate (see §1) — reclaim must run on granting replica; invariants `grace > sync interval` and `TTL > sync interval` are the deployment's job [verified: federation.md].
- HTTP authority vs git-remote mode: docs present Dolt remotes (git-protocol, DoltHub/S3/GCS/file) and dolt sql-server multi-writer as the paths; for multi-writer the recommendation is server mode / shared server / proxied-server ("For sustained concurrent agents, use server or proxied-server mode") [verified: architecture/dolt.md]. No doc explicitly frames an "HTTP authority mode" for federation; `bd serve` is a local work-surface, not a sync authority [inference].
- Bucket federation quickstart documents measured sync cadence via GCS/S3 [verified: https://beads.gascity.com/multi-agent/bucket-federation.md, not read in depth — single-source].

## 5. Operational reality
- Embedded mode (default): in-process Dolt engine (linked at Dolt 2.6.0), data at `.beads/embeddeddolt/`, **single writer enforced by file lock**; every bd invocation pays engine startup — docs explicitly warn loops calling bd hundreds of times pay it each time; use `bd batch` or server/proxied-server mode [verified: architecture/dolt.md (Modes of Operation, Embedded)].
- Server mode: `dolt sql-server` (port 3307 default; shared-server 3308 for multi-project machines; proxied-server managed mode; Unix socket option). Auto-commit defaults off in server mode (per-write DOLT_COMMIT under concurrency → 'database is read only' errors) [verified: architecture/dolt.md].
- Performance: `bd batch` exists specifically because "bd many times in a loop ... causes severe write amplification on a dolt sql-server" [verified: cli-reference/batch.md]. Bucket federation quickstart has measured timings [single-source]. No general write-latency benchmarks cited in docs I read; BENCHMARKS.md exists in repo root [verified: repo file listing, 2026-11-15] — not read.
- History growth: one Dolt commit per write by default (`dolt.auto-commit: on|batch|off`); mitigate with `bd compact` (age-tiered squash), `bd flatten` (single commit), `bd prune/purge` + `dolt gc --full` (generational GC — default pass misses squashed old-gen; must run `--full`). **v1.3.2-and-earlier `bd compact`/`bd flatten` hard-reset main and can discard concurrent writes**; fixed post-1.3.2 in CHANGELOG'd builds [verified: architecture/dolt.md (Maintenance; Writes that reach main)].
- Backup/restore: Dolt-native `bd backup init/sync/restore` (full DB incl. branches/history); auto-backup with 15m interval + 2GB size cap (a 2026-06-19 outage: 1.7GB store → 43GB backup dir) [verified: architecture/dolt.md; configuration.md (auto-backup)].
- Footprint: single Go binary; embedded needs no dolt install; Dolt pinned 2.6.0 floor enforced [verified: architecture/dolt.md].
- `bd serve` durability is per-request; no per-command auto-commit machinery, hooks don't fire [verified: cli-reference/serve.md].
