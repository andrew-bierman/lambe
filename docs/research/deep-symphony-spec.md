## 1. Normative conformance surface (MUSTs/SHOULDs)

- RFC-2119 keys defined at SP7-14; `Implementation-defined` behavior "MUST document the selected behavior" (SP12-14).
- Conformance is enumerated in **§18.1 "REQUIRED for Conformance"** (SP2212-2231): WORKFLOW.md loader (front matter+body), typed config layer with defaults + `$VAR` resolution, **dynamic WORKFLOW.md watch/reload (REQUIRED, §6.2 SP561-578: "MUST detect changes… MUST re-read and re-apply… Invalid reloads MUST NOT crash the service")**, polling orchestrator with single-authority state, tracker adapter with state-list + ID-refresh reads, workspace manager (sanitized, collision-resistant), the four lifecycle hooks, app-server subprocess client, strict prompt rendering (`issue`, `attempt`), exponential retry queue with continuation retries, reconciliation stopping runs on terminal/non-active states, terminal workspace cleanup, structured logs with `issue_id`/`issue_identifier`/`session_id`.
- Tracker contract MUSTs (§11): MUST support `fetch_issues_by_states` + `fetch_issues_by_ids` (SP1186-1208); empty input lists MUST return empty without a provider call (SP1199, SP1204); ID-refresh MUST fail on malformed requested records vs. state-list MAY omit+log (SP1221-1223); adapter MUST publish a compact profile (SP1246-1257); orchestrator MUST NOT inspect provider payloads or branch on provider semantics (SP1243-1244); normalization MUSTs (SP1261-1284: non-empty `id`/`identifier`/`title`/`state`, explicit `dispatchable`, JSON-safe `native_ref`).
- Workspace safety invariants (§9.5 SP928-948, §15.2 "Mandatory" SP1737-1740): agent cwd == per-issue workspace; workspace path MUST stay under root; sanitized keys `[A-Za-z0-9._-]` + ≥64-bit hash suffix if sanitization changed the identifier.
- Agent invocation (§10): launch `bash -lc <codex.command>` in workspace (SP970-971); MUST follow targeted Codex app-server protocol, which is "source of truth" and overrides the spec on protocol shape (SP958-962); session_id = `<thread_id>-<turn_id>` (SP1010); approvals/user-input MUST NOT stall a run indefinitely (SP1073-1075, SP1136-1139); each impl MUST document its approval/sandbox posture (SP1071-1072).
- Retry semantics (§8.4 SP796-811): continuation retry = fixed 1000 ms after normal exit; failure retry = `min(10000 * 2^(attempt-1), max_retry_backoff_ms)`; retry refresh via `fetch_issues_by_ids`; terminal-on-retry → clean workspace + release.
- State model (§7): internal claim states Unclaimed/Claimed/Running/RetryQueued/Released (SP641-660); scheduler state is **intentionally in-memory** — restart recovery is tracker+filesystem-driven, no durable DB (SP1690-1704). [inference] A durable-state Go implementation is a *superset*; nothing forbids durability, and §18.2 lists "Persist retry queue and session metadata across restarts" as a TODO/RECOMMENDED extension (SP2239).
- SSH workers: **Appendix A, entirely OPTIONAL** (SP2252+): `worker.ssh_hosts`, `worker.max_concurrent_agents_per_host`; orchestrator stays single source of truth; app-server launched over SSH stdio; continuation turns SHOULD stay on same host; post-side-effect reruns SHOULD be treated as new attempts (SP2286-2291).
- Test matrix §17 defines Core/Extension/Real-Integration profiles; "conforming implementation SHOULD include tests" (SP2051-2056).

## 2. Tracker interface (post-2026-07-20 generalization, PR #102 "Add generic tracker interface with Linear adapter")

- The orchestrator needs ONLY two read operations: `fetch_issues_by_states(state_names)` and `fetch_issues_by_ids(issue_ids)` (SP1186-1208). No claim, comment, close, or write op exists in the orchestrator contract. §11.5 (SP1310-1322): "Symphony does not require first-class tracker write APIs in the orchestrator" — ticket mutations are done by the *agent* via OPTIONAL provider-native agent tools executed host-side (adapter hooks `agent_tool_specs()`, `secret_environment_names()`, `execute_agent_tool(name, args, context={issue})`, SP1124-1132).
- Data model assumed = normalized Issue (§4.1.1 SP156-197): `id` (opaque dispatch ID), `native_ref` (opaque non-secret), `identifier` (unique human key, names workspaces), `title`, `description`, `priority` (1-4 rank), `state` (provider-native string, case-insensitive compare), `branch_name`, `url`, `assignee_id`, `labels` (lowercased), `blocked_by` (best-effort refs), `dispatchable` (REQUIRED adapter-derived boolean), timestamps RFC-3339.
- Claiming is **orchestrator-internal** (`claimed` set, SP289); the tracker never sees a claim. [inference] Multi-orchestrator fencing via tracker claims is *outside* the spec — Symphony assumes one orchestrator ("single authoritative orchestrator state", SP51; "The orchestrator is the only component that mutates scheduling state", SP637-638). A Beads-claim-fenced multi-orchestrator design is compatible but novel.
- **Beads mapping — fits well**: issues→Issue (id, identifier, title, description, state, priority, timestamps), labels→tags (normalize case), deps→`blocked_by`, comments/close→agent tools or Beads-native commands via an adapter tool. Beads statuses map to `active_states`/`terminal_states` by name. `dispatchable` can encode "claimed by another orchestrator" → false. [inference]
- **Concrete mismatches**: (a) Symphony has no claim primitive — you must encode fencing inside `dispatchable` or labels, and the spec's `dispatchable` is per-issue boolean computed adapter-side, so cross-orchestrator fencing lives entirely in your adapter [inference]; (b) `fetch_issues_by_states` filters by *state names* — Beads statuses are free-form/custom types, so the adapter must resolve configured names to Beads statuses and document the profile (SP1246-1257); (c) two-read contract means no comment/close in the core — a Beads adapter wanting the agent to comment/close must implement the OPTIONAL §10.5 tool extension (adapter-owned names/schemas, host-side execution, no secrets to child, SP1091-1120); (d) `bd` CLI vs HTTP: spec requires the adapter own transport/pagination/rate-limits (SP1232-1241) — HTTP preferred; shelling to `bd` is conforming but slower and harder to map errors to the §11.4 categories (`tracker_request`/`tracker_status`/…); (e) empty-list short-circuit MUST (no provider call) needs an explicit guard.
- Reference adapters shipped: linear, github, jira, asana, gitlab (elixir/README.md SP129-290 area) — proof the boundary is genuinely portable. [verified: elixir/README.md in repo]

## 3. Workspace & agent contract

- Lifecycle (§9): path `<workspace.root>/<workspace_key>` (SP859-861, default root `<system-temp>/symphony_workspaces` SP615); workspaces reused across runs, NOT deleted on success (SP864-866, SP1177); deleted only on terminal-state transitions (reconciliation SP835, retry SP807, startup sweep §8.6 SP841-849). Population (git clone etc.) is implementation-defined, typically in hooks (§9.3 SP888-901).
- Hooks (§5.3.4/§9.4 SP424-441, SP903-926): exactly four — `after_create` (only on new dir; failure fatal to creation), `before_run` (before each attempt; failure aborts attempt), `after_run` (after every attempt incl. timeout/cancel; failures logged+ignored), `before_remove` (before deletion; failures ignored, cleanup proceeds). Shell (`sh -lc` or stricter) with workspace as cwd, `hooks.timeout_ms` default 60000.
- Agent invocation (§10.1-10.2, §12): prompt = WORKFLOW.md body rendered with strict Liquid-like templating over `{issue, attempt}`; unknown var/filter MUST fail (SP499-502). Turn loop (§16.5 SP1932-1993): first turn = full prompt; after each successful turn re-fetch the issue; if still active+routable and under `agent.max_turns` (default 20), send *continuation guidance only* on the same live thread. Completion detection = targeted-protocol turn completion/failure/cancel, silence timeout `turn_timeout_ms` (default 1h), or subprocess exit (SP1018-1024). "Proof of work" appears ONLY in README/demo prose (CI status, PR review, walkthrough video) — it is **not normative**; spec-wise success just means the run reached a workflow-defined handoff state via agent-driven tracker writes (SP43-44, SP1321-1322). [verified: README.md line 8; SPEC has zero "proof" occurrences]
- Context/priming: no spec-level priming convention beyond the rendered prompt + workspace persistence; context assembly is §12 only.

## 4. Event/audit model

- Client→orchestrator events (§10.4 SP1039-1063): SHOULD include `event`, `timestamp`, `codex_app_server_pid`, optional `usage`; enumerated examples `session_started`, `startup_failed`, `turn_completed`, `turn_failed`, `turn_cancelled`, `turn_ended_with_error`, `turn_input_required`, `approval_auto_approved`, `unsupported_tool_call`, `notification`, `other_message`, `malformed`.
- Persistence: **none mandated.** Logs go to implementation-chosen sinks (§13.2 SP1379-1388); in-memory runtime state only (§14.3). OPTIONAL HTTP extension (§13.7) exposes `GET /api/v1/state`, `GET /api/v1/<issue_identifier>`, `POST /api/v1/refresh` with RECOMMENDED JSON shapes — the only interoperable machine surface. Consumers: operators/dashboards only; no spec'd audit trail. [inference] A durable event log is a compatible extension.

## 5. What "compatible" minimally means in practice

- The spec itself defines the bar: §18.1 checklist + §17 Core Conformance tests. There is no certification, no conformance test suite in-repo, and no trademark program. [verified: repo has no tests/ at top level; only elixir/test for the reference impl]
- De-facto bar observed in derivatives: implement WORKFLOW.md front-matter schema + hooks + per-issue workspaces + poll/claim/retry loop + the two tracker reads; agent backend and tracker are routinely swapped. Evidence: Rust reimplementation broomva/symphony keeps poll/workspace/`/api/v1/state` surface [verified: github.com/broomva/symphony]; ClaudeCodePSymphony swaps agent+tracker and encodes states as `symphony/*` GitHub labels [verified: github.com/gherghett/ClaudeCodePSymphony]; symfony-claude (sapsaldog) wraps Claude Code in the Codex app-server JSON-RPC shape [verified: sapsaldog.com/posts/symphony-with-claude-code]; oh-my-symphony forks the reference and adds backends/SQLite leases [verified: github.com/cskwork/oh-my-symphony]; contrabass is a Go reimplementation [verified: github.com/junhoyeo/contrabass]. None claims a formal conformance mark; they cite the spec.
- **Caller-named projects `fulcrum` (doctor conformance check), `github-symphony`, `paperclip`: not found in web search of the ecosystem — could not verify; treat as [single-source] from the caller.** The observed de-facto bar = WORKFLOW.md contract + workspace layout/lifecycle + two-read tracker adapter + poll/retry/reconcile loop; Codex app-server and the HTTP API are the most commonly substituted parts.
- Workspace layout is the least portable-once-deployed piece (keys, persistence, terminal cleanup); agent protocol is explicitly delegated to the targeted app-server version (SP958-962), so a different agent is conforming if the launch/turn contract is honored.

- Branding [inference, grounded in Apache-2.0 §6 + upstream's non-product posture]: calling a third-party project "Symphony-compatible" is nominally unprotected but OpenAI retains common-law/registered rights in "Symphony" (also a crowded field — many unrelated Symphony projects). Safe course: use "implements the OpenAI Symphony specification (Apache-2.0)" with attribution/NOTICE, avoid implying OpenAI endorsement, consider a distinct product name. Required Apache-2.0 mechanics: retain LICENSE/NOTICE attribution when deriving from the Elixir reference (the spec text itself is similarly licensed).
